# Overleaf and direct TeX editing

Use this workflow when a manuscript lives in Overleaf or the author wants directly editable TeX. Work in the project's actual `.tex` and `.bib` files once access and the requested scope are established. A chat draft may support the work but does not replace an authorized project edit. For an existing project, preserve its identity and layout; do not run the initializer over it, upload a replacement project, or overwrite it with the bundled fragments.

This reference defines an operational contract, not an Overleaf connector or API. A promised future connection, a project URL, a local checkout, and a GitHub commit each prove different things. Discover available tools and their actual permissions at execution time. Never invent tool names, endpoints, compilation results, or live connection status.

## Choose the route supported by observed capabilities

| Mode | Establish before using it | What completion requires |
|---|---|---|
| Connected editor/connector | Correct project; available file-list, read, write, revision, build, log, and PDF operations; each capability recorded separately | Read back changed source. Compile and inspect through available operations; explicitly name unavailable checks. |
| Direct Overleaf Git | Verified project Git remote, working authentication, advertised remote ref, and safe treatment of review metadata | Fetch current state, reconcile edits, push an authorized scoped change, read back the remote tree, and verify an Overleaf build if accessible. |
| GitHub bridge | Verified repository/branch and evidence that this exact Overleaf project has a configured link | A GitHub change followed by an actual Overleaf synchronization step and source readback. A GitHub commit alone is incomplete synchronization. |
| Exported source handoff | Current source archive/checkpoint, project settings where available, and an identified base version | Edited source or patch plus manifest and build evidence; say that Overleaf application is still pending. |
| Unconnected | No usable project access yet | Prepare useful TeX from supplied sources and identify the smallest missing access item. Do not claim an Overleaf edit. |

An account connection does not guarantee project edit access or compilation access. A Git integration is not a compiler. Keep authentication in the environment's approved credential mechanism; omit tokens, credential-bearing URLs, and private sharing links from logs and manifests.

Overleaf's Git bridge translates its collaborative history into Git and has limited Git semantics. Inspect actual remote refs instead of assuming a branch name; older clones and current clones may differ. Do not rely on remote feature branches, Git LFS, symlinks, or nested submodules. [Official Git integration documentation](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/git-integration).

Overleaf's built-in GitHub synchronization is explicitly initiated rather than automatic. Verify an existing link; do not assume an arbitrary existing repository can be attached to an existing project. Integration access and project-owner setup may be required. A link to a repository is not evidence that its latest commit is present in Overleaf. [Official GitHub synchronization documentation](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/github-synchronization).

## 1. Discover the project and establish a base

1. Resolve the intended project from the user's link, accessible project metadata, or the connected repository. If multiple candidates remain materially ambiguous, ask for the project identity while completing unaffected work. Preserve any local uncommitted edits; an isolated checkout may be useful for candidate changes.
2. Read the file tree, project instructions, build configuration, official template, root candidates, bibliography, macro files, and relevant section/appendix files. Inventory linked/imported files and generated assets. Identify whether any files must be updated at their upstream source instead of overwritten locally.
3. Read the **configured main document**, compiler, and TeX Live version from project settings when available. Record the source of every value: observed setting, log, repository configuration, or author-provided information. A filename or preamble can suggest a candidate but cannot prove the configured Overleaf root.
4. Resolve the dependency graph from that root through `\input`, `\include`, `\subfile`, and any `\import`/`\subimport` or project-defined inclusion macros. Follow bibliography and graphic paths, conditional compilation, `\includeonly`, shared preambles, and appendices. Static text search supplies candidates; it does not fully parse arbitrary TeX. Compile logs and generated dependency records can resolve dynamically selected inputs.
5. Save a recoverable base snapshot of files to be changed plus relevant settings, and record timestamp, available revision identifier/Git commit, and SHA-256 hashes of the original file bytes. Record the intended file/section scope, preserved local edits, active review metadata, and baseline build status. Keep this checkpoint outside submission inputs unless the author wants it there.

Overleaf uses a configured main document, but an open independently compilable file can become the target of a recompile. Thus a successful subfile build is insufficient evidence for the manuscript: verify the root actually used for the final build. [Official main-document documentation](https://docs.overleaf.com/getting-started/recompiling-your-project/the-main-document).

Compiler and TeX Live choices are project settings. Preserve verified choices when editing; a locally installed engine is not evidence that it matches the remote environment. Do not silently upgrade the distribution or switch engines to make a local build pass. [Official compiler and TeX Live documentation](https://docs.overleaf.com/getting-started/recompiling-your-project/selecting-a-tex-live-version-and-latex-compiler).

Use [overleaf-project.example.json](../assets/overleaf-project.example.json) as a project record. `null`, `unknown`, and empty collections mean not yet established, not a default to guess. `connection.mode` is one of `unconnected`, `connector`, `overleaf_git`, `github_bridge`, or `export_handoff`. In `settings_evidence`, attach each established field to its actual source/revision. Record dependencies as objects with `from`, `to`, `kind`, and `evidence`; record base hashes as path-to-SHA-256 mappings. Do not put secrets in this file. A newly scaffolded `main.tex`/pdfLaTeX choice describes only that local scaffold.

Overleaf History can identify, compare, label, and download available versions. A labeled checkpoint is useful when the operation exists and is within scope; an exported source snapshot should not be assumed to preserve all collaborative metadata. Do not restore an entire old version merely to undo this task's small edit. [Official History documentation](https://docs.overleaf.com/writing-and-editing/history-and-versioning).

## 2. Edit the smallest coherent TeX change

- Read the surrounding section, its evidence, dependent definitions, relevant comments, and main-text/appendix cross-references before editing. For an abstract request, inspect enough results to support its numbers without rewriting the whole paper.
- Keep existing class/style files, review/final switches, notation macros, citation commands/keys, labels, section split, and bibliography backend. Reuse established macros; do not expand them into inconsistent literal notation or add a parallel macro system. Change a global definition only when its full effect is understood and necessary.
- Write valid TeX in the owning file. Preserve comments and author TODOs outside the change; avoid whole-file reformatting. Escape prose special characters while respecting mathematics, URLs, and verbatim contexts. Update every affected label/reference when a justified rename is unavoidable, and check for duplicates and orphan references.
- Add verified bibliography records to the project's actual `.bib` source and deduplicate using identifiers and bibliographic identity. Keep existing keys stable. Determine whether the project uses BibTeX, Biber, another backend, or a supplied bibliography; inspect preamble, build configuration, and logs together. Do not replace a venue bibliography style to match a personal preference.
- Keep exact executed prompts in canonical files with recorded checksums. Presentation TeX should import or faithfully display them without paraphrasing, modifying whitespace-sensitive content, or dropping Unicode to fix compilation. Put role, model/version, variables, and source ID outside the prompt body. See [appendix-and-prompts.md](appendix-and-prompts.md).
- For new figures, use [figure-integration.md](figure-integration.md). Integrate the actual export, caption, semantic label, and textual callout into the file graph; verify the evidence and final-size rendering. For numerical figures/tables, preserve the analysis-to-asset provenance.

Multi-file projects can share preambles while allowing selected subfiles to compile independently. Preserve the project's chosen inclusion strategy and relative paths rather than flattening the paper. [Official multi-file project guide](https://www.overleaf.com/learn/latex/Multi-file_LaTeX_projects). With `biblatex`, the backend may be Biber or BibTeX, and bibliography resources are declared separately from the print command; a `.bib` extension alone does not identify the backend. [Official bibliography guide](https://www.overleaf.com/learn/latex/Bibliography_management_in_LaTeX).

## 3. Protect concurrent edits and review metadata

Before a write or synchronization, re-read the current revision and affected files. Compare **base**, **current**, and **proposed** content. Apply unchanged-base edits directly; merge nonoverlapping collaborator edits while preserving both intentions. If the same scientific claim, numeric value, macro, prompt, or paragraph has incompatible edits, retain both versions in a local conflict note and ask the author to choose only where evidence cannot resolve the conflict.

Prefer a connector's documented conditional update using a revision token or expected hash. A reread followed by a blind write is not atomic and cannot guarantee protection from a collaborator editing between the two operations. If the connector cannot guard writes and active overlap cannot be excluded, prepare the patch and use a supported safe editing route or an author-coordinated editing window. Do not repeatedly overwrite a changing file. Read back every applied change; if a write fails partway through a multi-file edit, record exactly which files were applied before retrying.

Treat comments and tracked changes as collaborative state. Inspect their availability, preserve them, and do not bulk accept/reject tracked edits, resolve/delete comments, or post messages to coauthors unless that action is authorized. Reviewing mode and tracked changes are distinct from a Git diff; do not claim one substitutes for the other. [Official Track Changes documentation](https://docs.overleaf.com/collaborating/track-changes).

Git pushes can lose or displace Overleaf comments and tracked changes; Git-side file moves/renames also threaten file metadata. Prefer a route that preserves active review state. If this cannot be verified, prepare a patch/handoff instead of silently risking that state. [Official Git limitations](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/git-integration). Pulling from GitHub into Overleaf carries a similar documented risk. [Official GitHub limitations](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/github-synchronization).

## 4. Build the actual manuscript and inspect it

Read [production-and-delivery.md](production-and-delivery.md). Use the project's documented build command and working directory after inspecting build scripts and `latexmkrc` for required behavior. If absent, derive the command from verified root/engine/backend settings. Do not execute an unknown script or enable shell escape merely to remove an error.

Capture a baseline build where feasible, then compile the candidate root with the required bibliography and reference passes. Tie logs and PDF to the source revision and settings, and record local versus remote execution separately. A stale PDF displayed after a failed recompile is not a successful candidate build. A local build with different TeX Live/packages is useful evidence with an explicit environment gap, not verified remote parity.

Read actual logs, including bibliography diagnostics: missing files, fatal errors, undefined commands, unresolved citations/references, duplicate labels, font problems, rerun requests, and material overflow. Fix the first causal error before interpreting cascades. Separate pre-existing defects from newly introduced ones; fix necessary scoped defects without concealing unrelated blockers. Never fabricate logs or infer success from a PDF filename. Overleaf exposes compilation diagnostics through its logs/output interface and supports stopping at the first error. [Official error-diagnosis documentation](https://docs.overleaf.com/troubleshooting-and-support/fixing-latex-errors).

Inspect the produced PDF at reading size, especially changed pages and displaced floats/page breaks. Check citations, math, captions, prompts, tables, appendix links, and main/reference/appendix page boundaries. The paper audit and any log checker are supporting checks, not substitutes for compilation, scientific validation, or visual inspection. If the environment cannot compile or render, report precisely which checks remain unverified and deliver the usable source change.

For a failed candidate, preserve the patch, log, first actionable error, affected path/location, and last known successful revision. Revert only this task's defective change when appropriate; never discard intervening coauthor work or restore the whole shared project as a shortcut. Repeat only checks affected by the repair.

## 5. Apply, synchronize, and report the observed state

Complete authorized in-place edits and necessary verification without asking the author to reapprove routine work. A writing request does not itself authorize a new public repository, a new integration, a repository-visibility change, publication, or conference submission. Keep a concrete patch/build report ready before requesting any genuinely missing authorization or access.

**Connector route:** verify the project identity and current base, apply guarded scoped edits, read them back, and run the available build/log/PDF operations. Record the new revision if exposed. If the connector can write but cannot compile, report source saved and remote build unverified as separate states.

**Direct Git route:** use a local branch/checkout for preparation if useful, but query the project's advertised remote refs and use the verified destination. Fetch before integration; merge or rebase without losing source or collaborator changes, then review the resulting complete diff and build it. Immediately before an authorized ordinary push, refresh the remote state. A non-fast-forward rejection requires reconciliation and revalidation, never an automatic force push. Read back the remote tree after a successful push; verify the Overleaf build separately when accessible. Do not reset shared history, replace the remote, or use `--force`/`--force-with-lease` as a routine conflict solution.

**GitHub bridge route:** record the repository commit and the actual synchronization step separately. Refresh both sides before merging. If Overleaf creates a conflict branch, inspect both histories, resolve the scientific/textual conflict, and repeat synchronization through a supported operation; do not delete the competing work. The native integration may create a branch when reconciliation fails. [Official synchronization conflict behavior](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/github-synchronization). If the required Overleaf operation is unavailable, deliver the prepared change with the exact remaining action and say **GitHub updated; Overleaf synchronization not verified**.

**Export route:** deliver changed source files or a patch against the recorded snapshot, required new assets, a file/hash manifest, and validation notes. Explain the files and base revision to which it applies. Do not imply that uploading a ZIP preserves project settings, review metadata, or current collaborator edits. Say **source prepared; Overleaf application pending** until actual readback establishes otherwise.

Final reporting should identify the project and scope without exposing credentials, list changed files, state the base and resulting revision where known, distinguish local/remote build results, name PDF/visual checks, record synchronization evidence, and list remaining scientific or technical blockers. Only say **updated in Overleaf** after actual source readback; only say **compiled in Overleaf** after observing the corresponding successful build.
